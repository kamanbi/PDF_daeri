# 무손실 PDF 파이프라인 구현 절차

## 이 스킬이 지키는 것

편집은 **페이지 참조 목록의 재배열**이다. 원본 바이트를 건드리지 않는다.
100페이지 텍스트 PDF에서 한 장을 지워도 결과는 여전히 텍스트 PDF여야 하고, 용량은 줄어야 한다.

래스터화 한 줄이 이 제품의 존재 이유를 없앤다. 그래서 아래 절차는 "하지 말 것"을 코드 구조로 봉쇄한다.

## 1. 페이지 모델

```dart
sealed class PageRef {
  final int rotation; // 0/90/180/270
}

class ImagePageRef extends PageRef {   // 스캔·사진
  final String imagePath;
}

class PdfPageRef extends PageRef {     // 외부 PDF 또는 앱 내 PDF
  final String sourcePath;   // 앱 작업공간의 원본 복사본
  final int sourceIndex;     // 원본에서의 페이지 번호
}
```

한 문서에 **두 종류가 섞인다**(외부 PDF + 스캔 페이지 = 혼합 문서). 저장·렌더·편집의 모든 분기가 두 종류를 모두 처리하는지 확인한다. `sealed`를 쓰는 이유는 컴파일러가 누락 분기를 잡게 하기 위해서다 — `default:`/`_:`로 뭉개면 이 보호가 사라지므로 쓰지 않는다.

## 2. 저장 절차 (`PdfEngine.save`)

| 페이지 종류 | 처리 | 손실 |
|---|---|---|
| `PdfPageRef` | 원본에서 **페이지 객체 import** | 없음 |
| `ImagePageRef` | JPEG 임베드 (quality 프리셋) | 이미지 인코딩만 |
| 회전 | 페이지 **회전 속성만 변경** | 없음 |

**저장 경로에서 금지되는 것:**
- PDF 페이지를 비트맵으로 렌더링해 다시 넣기 — 어떤 경우에도
- 이미지 재인코딩 — 그것은 `pdf_compressor.dart`의 몫
- 증분 저장(incremental save) — 항상 **전체 재작성(full rebuild)**

구조적 봉쇄: `pdf_engine.dart`는 `pdf_renderer.dart`를 **import 하지 않는다**. 렌더러는 UI 썸네일 전용이다. 저장 파일이 렌더 API에 접근할 수 없으면 래스터화 사고가 물리적으로 불가능해진다.

## 3. 용량 증가 3대 함정

| 함정 | 증상 | 대응 |
|---|---|---|
| 증분 저장 | 페이지를 지웠는데 용량 그대로/증가 | 항상 전체 재작성 모드 |
| 고아 객체 | 페이지만 삭제되고 리소스 잔존 | 재작성 시 미참조 객체 제거 |
| 폰트·리소스 중복 | 합치기 결과가 원본 합보다 큼 | 저장 시 리소스 중복 제거. 라이브러리 미지원이면 사용자에게 경고 |

라이브러리가 중복 제거를 지원하지 않으면 **임의 우회 구현을 만들지 말고** 제약으로 보고한다. 이는 `milestones.md` 1주차 판정(라이브러리 교체) 사유다.

## 4. size_guard 게이트 작성법

저장 **직전**에 통과해야 하는 관문이다. 저장 후 확인이 아니다.

```dart
enum SaveOp { deletePages, reorderOrRotate, split, merge }

sealed class GuardResult {}
class GuardPass extends GuardResult { final int resultBytes; }
class GuardBlocked extends GuardResult {
  final int resultBytes;
  final int limitBytes;
  final SaveOp op;   // 사용자에게 무엇이 왜 막혔는지 전달하기 위함
}
```

| 작업 | 규칙 |
|---|---|
| 페이지 삭제 | `결과 ≤ 원본` |
| 순서 변경·회전만 | `결과 ≤ 원본 × 1.05` |
| 나누기 | `결과 ≤ 원본 × (선택페이지 / 전체페이지) × 1.2` |
| 합치기 | `결과 ≤ 원본 합계 × 1.05` |

작성 규칙:
- 비율 상수(1.05, 1.2)는 이름 있는 상수로 분리한다. 호출부에 흩어지면 조용히 완화된다.
- `GuardBlocked`는 예외가 아니라 **정상 흐름의 한 갈래**다. `throw`로 만들면 상위에서 `catch {}` 한 줄로 무력화된다.
- 게이트 위반 시 임시 파일을 정리하고 `docs/<docId>/`를 롤백한다.
- **이 규칙들은 유닛 테스트로 고정한다.** 픽스처 3종(텍스트 PDF / 스캔 PDF / 혼합 문서)으로 매 빌드 검증한다.

## 5. 압축 (편집 저장과 완전 분리)

압축은 **의도적 손실**이다. 코드·UI 모두 편집 저장 경로와 분리한다.

1. **대상 판별** — 페이지가 이미지 위주(스캔본)인가
   - 이미지 위주 → 재인코딩 진행
   - 텍스트·벡터 위주 → 실행하지 않고 "이 문서는 압축 효과가 거의 없습니다" 안내
2. **결과 검증** — 결과가 원본보다 크면 **자동으로 원본 유지** 후 알림
3. **결과 표시** — `4.2MB → 1.1MB (74% 감소)` 형태로 숫자 제시

| 프리셋 | 긴 변 최대 | JPEG 품질 | 용도 |
|---|---|---|---|
| high | 2480px | 85 | 도면·작은 글씨 |
| standard | 1754px | 75 | 기본값 |
| min | 1240px | 60 | 메일 첨부 |

**이 표는 1주차 실측 후 갱신 대상이다.** 판정: `min`으로 10페이지 스캔 문서가 2MB 이하이면서 본문이 읽혀야 한다. 실측 전에는 잠정값으로 다루고, 갱신 시 `pipeline.md`도 함께 고친다.

## 6. 메모리·isolate

- 페이지를 한 번에 메모리에 올리지 않는다.
- PDF 파싱·병합·압축은 **isolate에서 실행**한다. 비동기만으로는 UI가 멈춘다.
- isolate로 보내는 데이터는 직렬화 가능해야 한다 — `PageRef`를 그대로 보낼 수 있는지 설계 단계에서 확인한다.
- 50페이지 이상은 진행률 + 취소를 지원한다. 취소 시 부분 산출물을 남기지 않는다.

## 7. 실패 경로 (전부 처리해야 완성)

공간 부족 / 권한 거부 / 손상 파일 / 암호 PDF / 사용자 취소 / 게이트 위반.
저장 실패 시 `docs/<docId>/` 전체 롤백. 반쪽 문서를 목록에 남기지 않는다.

## 8. 구현 후 자체 점검

- [ ] `pdf_engine.dart`가 `pdf_renderer.dart`를 import 하지 않는가
- [ ] 저장 경로에 `render`/`toImage`/`Canvas` 계열 호출이 없는가
- [ ] 모든 저장 진입점이 `size_guard`를 경유하는가
- [ ] `GuardBlocked`가 사용자에게 도달하는가 (삼켜지지 않는가)
- [ ] `PageRef` 분기가 두 종류를 모두 처리하는가 (`default:` 없이)
- [ ] 회전이 재인코딩 없이 속성만 바꾸는가
- [ ] 압축이 편집 저장 경로와 파일·UI 모두 분리되어 있는가
- [ ] isolate 경계를 넘는 데이터가 직렬화 가능한가
